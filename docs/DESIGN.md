# 設計メモ ―― AI に「判断」させない

このプロジェクトの根本制約は **「AI にコマンドを任意に作らせない」**、
さらに **「診断スクリプトも AI に選ばせない」**。AI が担うのは、出力の **要約** だけ。

| AI がやること | AI がやらないこと |
|----------|--------------|
| スクリプト出力を人間向けに 2〜4 文へ要約する | コマンドを自分で生成する |
| | SSH 先で自由にシェル操作する |
| | 診断スクリプトを選ぶ（対応表で決定） |

多機能な「何でもできる」エージェントは便利だが、乗っ取られたら何でもされる。
自宅のサーバに強い権限を渡さないため、実行できるのは**事前に許可した読み取り専用スクリプト**に限り、
どれを走らせるかも表引きで機械的に決める。AI に与える自由度を最小化する設計。

---

## なぜスクリプト選択から LLM を外したか

初期版は「許可スクリプト 6 本から LLM が 1 つ選ぶ」設計だった。これを表引き（`ALERT_TO_SCRIPT`）に変えた理由：

1. **選択は機械的に決まる。** 発火しうる alertname は自分で書いた Alertmanager ルールで閉じている（未知のアラートは来ない）。`alertname × OS` の対応表で 100% カバーできる。
2. **クォータが貴重になった。** ローカル推論なら呼び出しコストはゼロだが、クラウドの無料 LLM API に移すと 1 アラートあたり複数回の呼び出しが効いてくる。無料枠は予告なく削減されうる。表引きなら消費ゼロ。
3. **決定的でテスト可能。** LLM 選択は非決定的で、失敗時のフォールバック（OS 別固定）は alertname を見ないため「ディスクのアラートにメモリ診断が走る」ような実害が出た。表引きは常に同じ結果。
4. **設計思想に合う。** 「AI に自由度を与えない」方針の徹底。AI らしさの本丸は"選択"ではなく"要約"（人に分かる言葉へ翻訳すること）だ。

**アラートルールを増やしたら、この対応表にも行を足すこと**（足し忘れてもログ全般調査スクリプトに落ちるだけで事故にはならない）。

## LLM 呼び出しの堅牢化（クラウド API 前提）

要約に使う LLM（Gemini 等）はクラウド API のため、無料枠と一時エラーに耐える必要がある：

| 状況 | 挙動 |
|------|------|
| 429 で日次枠(RPD)超過（body の quotaId に `PerDay`） | **リトライせず即フォールバック**。翌日まで回復しないものに連打してもクォータを消費するだけ |
| 429（毎分枠 RPM）/ 503 | body の `RetryInfo.retryDelay` 秒だけ待って再試行（上限つき／無ければ指数バックオフ・最大 3 回） |
| 400 / 401 / 403 | 即諦め（`API_KEY_INVALID` 等はリトライ無意味） |
| 呼び出しがハング | ハード上限で見切って `None`（スケジューラ全体は止めない） |
| 要約が最終的に `None` | スクリプト生出力を添付して通知（**通知は必ず出す**） |
| Telegram が 400（Markdown パース失敗） | parse_mode 無しの平文で再送（メトリクス名の `_` `*` が原因になりうる） |

- **無料枠の RPM 超過を防ぐため、呼び出し間隔に下限**（スロットル）を設ける。
- **API キーはヘッダで渡す。** クエリパラメータに載せると、requests の例外メッセージ（URL 込み）経由でログに漏れる。
- **Bot トークンは URL 仕様上必ず URL に入る**ため、例外メッセージをそのままログに出さない（マスクする）。

## 教訓（運用で血を流して学んだこと）

- **無料枠の公称値を信用しない。** 提供側は予告なく変える。実枠は 429 応答の body / プロバイダのダッシュボードで確認する。
- **エラーレスポンスの body を読む。** ステータスコードだけでは「待てば直る 429」と「待っても無駄な 429」を区別できない。
- **`.env` を変えたら必ずサービスを再起動する。** 旧設定のプロセスが走り続け、無効化済みのキーで叩き続ける事故になる。
- **リトライは無条件の善ではない。** クォータ課金されるエラーへのリトライは自傷行為。
- **前提が変わったら構造を見直す。**「ローカル推論だから呼び放題」前提の呼び出し構造は、クラウド API 移行後には破綻する。
- **フォールバック設計は正しかった。** LLM が死んでも通知は 1 件も落とさない。「要約は死んでも、異常を知らせる仕事は生き残る」方針は維持する。
